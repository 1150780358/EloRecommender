## 〇、研发环境:算力硬件与 AI 协作方式(贯穿四周)

### 算力与硬件:现有资源 vs 实际占用

| 资源 | 现有配置(共享 GPU 服务器) | 实际占用 |
|---|---|---|
| CPU | AMD EPYC 7542,32 核 64 线程 | 训练固定 **16 线程**(约全机 1/4;实测 32+ 线程在中小样本上同步开销反超收益,反而更慢) |
| 内存 | 128 GB | 2900 万行交易经列类型降精度压缩后单机全量处理,常驻远低于机器上限,无需分块/分布式;特征构建 3.7 分钟、端到端 25.3 分钟 |
| GPU | 2× NVIDIA RTX 4090(24 GB) | GBDT 主线 **0 卡**;仅 v5 异构基学习器(torch MLP×2)短时占用 1 卡 |
| 存储 | /data 7.3 TB 共享盘 | 项目全量约 **4.4 GB**(原始数据 + `outputs/` 基模型产物 + refs 开源仓库) |
| 软件环境 | conda(Python 3.11)+ CUDA torch | base 环境覆盖全部依赖;`requirements.txt` 固化版本 |

> 结论:本课题对算力的实际需求远低于机器配置——**16 CPU 线程 + 数十 GB 内存、无 GPU 依赖**即可完整复现主线结果,GPU 仅为异构模型实验的可选项。

### AI 辅助研发(Claude Code + Claude Fable 5)

全程采用 **Claude Code**(Anthropic 官方终端智能体,驱动模型为 Claude 5 家族的 **Fable 5**)作为结对研发工具,在服务器终端内直接读写仓库、执行实验。四个阶段的分工方式:

1. **调研阶段**:AI 通读开源仓库全部 notebook、抓取论坛一手复盘,逐条核验"自述招数是否有代码证据";人负责提问框架与结论把关;
2. **方案阶段**:人给出目标与约束、AI 起草备选与权衡,经对话评审定稿;
3. **编码与实验阶段**:结对编程(AI 写代码、人做设计决策与结果判读);**无人值守战役脚本**(特征重建→全套重训→择优提交→记录回填)由 AI 编写并跨夜自主运行;
4. **文档与工程化**:任务日志、周报、泄漏审计、README 由 AI 起草、人审定;Git/GitHub 由 AI 执行(仓库级 deploy key 安全配置)。

**协作纪律(人机边界)**:方向取舍、提交判据、成绩口径由人最终拍板;AI 产出的任何改动一律经离线交叉验证与线上验证后才采信;多会话并行以「写前查改动时间、并入而非覆盖」约定防冲突;全部改动进 Git。

## 第 1 周(07-27 ~ 08-02):赛题调研与数据理解 —— 答辩维度「项目分析与理解」

### 本周思路(我的想法)

- **先看清问题再动手**:首次接触该数据集,我把第一周定为"只调研不建模"——方向判断错了,后面做得越多浪费越多;但要跑通一个最简基线,让后续每个改进都有参照。
- **本周最重要的认识转变**:数据摸底发现约 1% 的评分是固定极端负值(-33.219),且贡献了误差的大部分。我由此判断这道题实际是**"识别极端异常客户"(类风控异常检测)+ "普通客户常规打分"(回归)两个问题的叠加**,不能当普通回归做——这一判断后来被所有前排方案印证,成为整个技术路线的骨架。
- **业务上的理解**:忠诚度评分是金融机构客户精细化管理的抓手;那 1% 极端客户业务上对应"深度流失/问题客户",本就该单独对待——技术方案与业务直觉在这里互相印证。
- **对评价体系的警惕**:了解到公开榜仅 30% 样本、终榜大洗牌,我决定一切改进以本地分层交叉验证为准,公榜只作通道验证——先建立自己信得过的评价方法,再谈优化。

### 一、工作进度

1. **赛题背景调研**:业务目标(依据持卡人历史交易预测忠诚度评分)、评价指标(RMSE)、数据构成(约 32 万卡、2900 万行交易、商户表);确认本赛已截止,属 Late Submission(正常评分、不进官方榜),明确"等效名次"成绩口径。
2. **Top 方案与开源代码分析**(成文 `docs/202607/31-Top方案对比分析.md`):以公开 kernel 级 baseline 为参照,逐方案分析前排"多做了什么"——取得 1st/5th/7th/10th/11th/16th/18th/19th/21st/22nd 等十余份一手复盘;前 10 仅 7th 开源完整代码,21st/63rd 两个完整代码仓拉取至 `refs/` 逐仓核验;横向对照 + 频次统计识别出高频增量(序列嵌入/大融合/month_lag 深挖/行级元特征)与明确空白;差距归因分解(特征深度可追、模型农场边际成本高、私有洞察部分可复现)→ 定下"特征优先、不堆模型农场"的资源策略。
3. **官方数据文件分析与摸底**(成文 `docs/202607/31-官方数据文件分析.md`):7 个官方文件逐一分析;关键事实——官方无 baseline 代码;target 1.09% 哨兵值;installments 哨兵与 category_3 缺失同源;month_lag 是各卡不同参考月的隐藏时间对齐轴;merchants 表 63 个重复 id;2900 万行单机可行性摸底。
4. **验证与提交策略**:公榜不可信 → 确定以折外交叉验证(OOF)为唯一择优判据。
5. **复现 baseline 并首次提交**:以 63rd 精简复现(基础聚合 + LGB 分层五折)跑通「数据→特征→训练→预测→提交→分数回流」全链路,登记为对照基准【baseline 分数以 submissions.md 为准】。
6. **过程管理**:调研文档、提交台账、环境搭建全部就位。

### 二、学习收获

1. 先分析目标变量的"分数结构"再动手——1% 异常值决定方案骨架,分析先行的价值在本周直接兑现;
2. 调研要区分"文字复盘"与"可核验代码",只有代码证据能进移植清单;调研的终点是资源分配决策,不是知识清单;
3. 业务直觉可以校验技术方向(异常客户单独建模);
4. 评价体系的可信度是一切优化的前提("信本地验证不信公榜");
5. AI 工具负责广度(一天完成数天的代码考古),人负责判据——结论必须自己核实。

### 三、下一周工作计划

- 基于本周判断撰写**总体技术方案**:清洗规则、特征体系、"异常识别 + 分层回归"模型架构、分层十折验证设计;
- 制定实验管理与提交纪律(先离线验证、后上线确认);
- 规划工程结构与自动化实验方案。

## 第 2 周(08-03 ~ 08-09):总体技术方案设计 —— 答辩维度「建模流程与实施方案」

### 本周思路(我的想法)

- **验证体系先于模型**:我把方案的第一章留给验证而不是模型——CV 怎么切(按异常值分层保证每折比例一致)、判据是什么(OOF 降低且 CV-LB 偏移不缩小)、噪声多大(折间波动)不先定义,后面所有"改进"都无法判真伪。这个顺序是我从第 1 周"公榜不可信"的教训里推出来的。
- **架构服从问题结构**:既然题目是"异常识别 + 常规打分"的叠加,模型层就设计为三路——全量回归、异常二分类、剔除异常的干净回归,再用融合把三路合起来;而不是先选一个"最好的模型"。
- **把实验吞吐当成设计目标**:提交额度有限、四周时间有限,我在方案里专门设计了两件提效的事:基模型预测统一落盘(融合实验从每次重训 10 分钟降为秒级)、无人值守战役脚本(夜间也在产出结果)。我的想法是:**迭代速度本身就是竞争力**。
- **风险先写进方案**:公榜不可信→写死纯 OOF 择优;无官方名次→计划取回真实私榜分数表建立等效名次标尺;复现性→固定随机种子。预案先行,后面执行就不纠结。

### 一、工作进度

1. **总体技术方案文档**(数据→特征→验证→模型→实验管理五层):业务化分层清洗(哨兵值按缺失机制归位、金额脱敏还原、商户表去重);约 200 维特征体系三族(聚合统计/时序/交叉)+ 两道筛选闸;按异常值分层十折,OOF 唯一判据 + CV-LB 偏移警报;LGB/XGB/CatBoost + 异常二分类 + 干净回归,二层 Ridge Stacking 与加权融合对照,预留 huber/多 seed 扩展位;提交必有离线支撑、必回填台账。
2. **工程方案**:`src/ + scripts/ + docs/ + outputs/` 四目录;基模型产物统一 npz 协议;无人值守战役脚本设计(支持跨夜)。
3. **风险预案**:公榜、名次口径、复现性三项预案入方案。
4. **方案评审与排期**:与指导老师对齐;排定第 3 周编码首提、第 4 周深化优化里程碑。

### 二、学习收获

1. 方案文档的价值在"决策与理由"而非"步骤"——每个设计点写清备选与取舍,后期实验矛盾时能回溯是假设错了还是执行错了;
2. 验证体系要先于模型设计,这是我对"建模流程"最大的观念更新;
3. 解耦(融合与重训分离)与自动化是小团队高吞吐的关键设计;
4. 实验纪律本质是资源约束下的最优策略——把有限的提交额度全部花在有信息量的验证上。

### 三、下一周工作计划

- 按方案实现端到端管线,完成自研管线首提(v1),量化对 baseline 的提升;
- 搭建自动提交回填与无人值守战役;
- 启动快速迭代(锚定特征、调参、开源方案特征移植、多 seed);
- 经 Kaggle API 建立私榜等效名次标尺。

## 第 3 周(08-10 ~ 08-16):管线编码与首轮实验(v1→v4)—— 答辩维度「特征工程与模型选取训练」

### 本周思路(我的想法)

- **先跑通、再优化、每步留证**:管线一次成型后,我坚持小步迭代——每轮只改一类东西(特征/参数/模型),离线验证通过才提交,这样每 0.001 的提升都能说清来源;这也是答辩时"建模流程"可以拿出证据链的原因。
- **把名次标尺做准**:拿到真实私榜 Top200 分数表后发现,首提成绩实际已在银牌线(此前按公开资料估成铜牌线外)。我的体会:**衡量尺度不准,努力方向就会错**——这件"非建模"的事优先级其实很高。
- **对调参的判断**:Optuna 复搜一轮仅改善 0.00009,而特征改动动辄 0.002~0.003。我据此把调参降为收尾手段,资源全部转向特征——与第 1 周"特征优先"的调研结论闭环。
- **工程问题的排查观**:训练变慢、结果不可复现这类问题,我按"先量化、再假设、再对照实验"排查(线程同步开销、浮点累加顺序),而不是凭感觉换配置。

### 一、工作进度

1. **端到端管线**(`src/elo_pipeline.py` 约 1200 行):清洗、196 维特征、分层十折、多回归 + 异常二分类 + 干净回归、Stacking 与加权融合、产物落盘;全量 25.3 分钟(特征构建 3.7 分钟)。
2. **自动化基础设施**:提交后自动轮询评分回填台账;战役脚本无人值守(含跨夜)。
3. **私榜真实标尺**:Kaggle API 取回 Top200 真实分数(`outputs/private_lb_top200.json`),建立精确等效名次换算。
4. **v1→v4 四轮迭代**(每步均有离线支撑):

   | 版本 | 关键改动 | OOF | Private | 等效名次 / 4111 |
   |---|---|---|---|---|
   | v1 | 三模型 Ridge Stacking(自研首提,超越 baseline) | 3.64362 | 3.61276 | ~210(银牌线边缘) |
   | v2 | + 观察月锚定特征 + 干净回归后处理 | 3.64195 | 3.60974 | 114 |
   | v3 | + Optuna 终选参数 | 3.64228 | 3.60965 | 112 |
   | v4 | + 移植特征(众数/序列嵌入/逐月透视斜率/算术交叉)+ huber 基模型 + 3-seed 平均 | 3.63670 | 3.60759 | **69(top 1.7%)** |

5. **工程问题排查**:32 线程同步开销致慢 → 固定 16 线程;huber 不可复现 → 定位浮点累加顺序 × 平坦验证曲线 → deterministic 解决;公榜背离 → 按预案弃用。

### 二、学习收获

1. 特征 >> 调参(0.003 vs 0.00009),资源要投在信息增量上;
2. "不可复现"是可逐折二分定位的工程问题,不是玄学;
3. 多 seed 平均是低风险稳定收益;
4. 度量基础设施(名次标尺、提交台账)的优先级被普遍低估;
5. 无人值守自动化让夜间也产出结果——吞吐靠基础设施而非加班;
6. 人机结对分工:人提假设、AI 快速做对照实验,排查类问题效率倍增。

### 三、下一周工作计划

- 系统验证融合层/异构模型方向的收益(存疑,需证据);
- 主攻"引入新信息":折内目标编码、交易时间差分布等调研识别的空白;
- 泄漏审计、工程化沉淀、技术报告与答辩材料;
- 判据纪律:OOF 降低 >0.0005 且偏移不缩小方可上线;目标逼近金牌线(3.60078)。

## 第 4 周(08-17 ~ 08-23):深化实验(v5→v8)、突破金牌线与总结 —— 答辩维度「模型评估、发现与创新、最终效果」

### 本周思路(我的想法)

- **给每类改进算"转化率"**:v5 让我发现离线改善不一定兑现到线上(转化率仅 2%),我开始把「OOF 改善 → 线上改善的转化率」作为评估改进类型的指标,并总结出规律:**结构优化 2% << 折依赖的编码特征 45% << 折外无依赖的行为特征 119%**——"这个改动引入了什么新信息、其计算口径是否依赖折划分"成为我立项的前置两问。这是本项目我最想在答辩里讲的发现。
- **把风控思维用在自己身上**:TE-v2 离线大幅改善、上线反而恶化的事故后,我提出**泄漏警报线**制度(单一改动 OOF 改善超 0.003 一律先视为泄漏嫌疑,三重审计通过才可上线)。v7 的时间差特征同样触线,但对抗验证/逐折一致性/机制核验三关全过后放行——事实证明它是真信号。**警报线是"先审计"的触发器,不是"一律不上"的封禁线**,这与银行风控"红线 + 尽调"的逻辑一致。
- **负结果也是资产**:v5 四方向、v8 行级元特征的证伪都完整记录并归因——v5 的证伪直接指出了 v6/v7 的正确方向;v8 的失败(连同社区旁证)让我判断"冠军的私有洞察不可由公开资料复现",从而理性收手,不再消耗资源硬攻。
- **对最终位置的判断**:第 16 名(金牌区)之后,剩余候选的先验收益都低于噪声水平。我认为**知道"天花板在哪、为什么"与冲到天花板同样重要**——这就是答辩里"项目效果"一节的收束方式。

### 一、工作进度

1. **v5 战役:四方向系统性证伪**(负结果):融合层重构 / 异构基学习器(MLP、ExtraTrees)/ 分类器增强 / 增量特征族——20 余个融合方案同折对比,OOF −0.00285 但 Private 仅 −0.00006;机制归因:stacking 对高方差成员的折平均降噪偏差使二层高估其价值。
2. **v6 战役:目标编码突破**:移植 21st 折外 outlier 率目标编码并三处改进(严格折内统计防泄漏、贝叶斯平滑、连续键离散化)→ **Private 3.60635,第 59 名**,转化率 45%;附带发现 CatBoost 与外部 TE 冗余。
3. **TE-v2 泄漏事故与审计制度**:键集扩展版离线骤降 0.0077、上线反恶化 0.0059 → 判泄漏回滚;由此建立**泄漏警报线**并完成全特征泄漏专项审计(`30-数据泄露审计.md`),泄漏产物全部清除。

### 二、学习收获

1. **改进类型决定收益真伪**(核心发现):转化率梯度 2% / 45% / 119% 对应结构优化 / 折依赖编码 / 折外行为特征——评估新改动先问"引入了什么新信息、口径是否折依赖";
2. **泄漏防控要制度化**:警报线 + 三重审计(对抗验证/逐折一致性/机制核验)能把"真泄漏(TE-v2)"与"真信号(v7)"可靠区分——单凭离线分数无法区分二者;
3. **Stacking 方差陷阱与"OOF 元特征禁入一层"**:两条融合层的结构性教训,前排方案复盘与我们实验互相印证;
4. **负结果的完整记录是方向盘**:v5 证伪指出 v6/v7 方向,v8 证伪确认天花板,避免无谓消耗;
5. **知道边界也是能力**:公开资料可复现的部分已全部收割(21st 四招、Top1/7th 核心招验证),16 名即公开资料天花板附近——对"为什么停在这里"的论证与成绩本身同样有说服力;
6. **AI 时代研发的分工再认识**:AI 改变广度与吞吐(代码考古/批量实验/文档),人守判据与取舍(立项两问、警报线、成绩口径)——判断环节恰是价值密度最高的部分。
