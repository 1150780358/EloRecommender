# 实习周报（第一周）

**报告人**：×××（数据分析部实习生）
**报告周期**：2026年7月27日—8月2日
**实习课题**：信用卡线上支付用户忠诚度评分预测（Kaggle Elo 赛题）

## 一、我对课题的理解与本周工作思路

**对业务问题的理解。** 本课题要求利用某支付机构的信用卡基本信息、交易流水和商户数据，预测客户的忠诚度评分。我理解这件事对金融机构的价值在于：忠诚度评分是客户精细化管理的"抓手"——分数高的客户值得投入资源做个性化推荐和权益运营，分数异常低的客户则可能是流失或风险苗头，需要提前干预。三类数据恰好对应"客户是谁—做了什么—在什么场景"，本质上是**从行为数据刻画客户关系质量**，这与银行日常的客户画像、分层营销工作是同一套逻辑。

**我对解题路径的考虑。** 考虑到自己是首次接触该数据集，我给自己定的原则是"先看清问题，再动手建模"：第一周不急于训练模型，而是把功夫花在三件事上——弄清评分数据本身的规律、学习前人的成熟经验、跑通一个最简单的基线把全流程走一遍。我的想法是：方向判断错了，后面做得越多浪费越多；而基线跑通了，后续每一个改进才有可对比的参照。

**本周一个关键发现改变了我对题目的认识。** 在数据摸底中我发现：约1%的客户评分是一个固定的极端负值，而正是这1%贡献了误差的大部分。我由此意识到，这道题实际上是**两个问题的叠加**——"识别出极少数极端异常客户"（更像风控中的异常检测）加上"给普通客户常规打分"（回归问题）。这个认识后来在头部方案调研中得到印证：几乎所有高分方案都是围绕这1%做文章的。我认为这是本周最重要的收获——它决定了后续整个技术方案的骨架，也让我体会到"分析先行"的价值。

## 二、本周主要工作

一是**数据摸底**：逐一分析官方7个数据文件的规模、含义与质量问题（评分中的极端异常值、若干字段的哨兵值与缺失同源现象、商户表重复记录等），形成数据分析文档；二是**先进方案调研**：系统梳理了原赛前排十余份公开复盘与三个开源代码库，逐条核对"哪些经验有代码依据、哪些只是说法"，整理成对比分析文档，并据此拟出可借鉴清单；三是**基线复现**：以社区开源实现为底完成简化复现，跑通"数据—特征—训练—预测—平台提交—取回分数"全流程（赛题官方不提供基线代码，此环节同时验证了考核所需的提交通道正常）；四是完成环境搭建与文档、提交台账等过程管理规范。

## 三、学习收获与思考

**（一）业务与技术要互相印证。** 那1%极端客户在业务上大概率对应"深度流失/问题客户"，本就该与普通客户分开对待；而技术上"先识别、再分开建模"的方案恰与这一业务直觉一致。我体会到：模型方案能否讲出业务道理，是判断方向对不对的重要参考，这一点在将来答辩中也应作为主线来讲。

**（二）评价体系比单次成绩更重要。** 调研中了解到本赛题的公开排行榜仅基于30%样本、历史上终榜排名大幅洗牌，前排选手反复强调"相信本地验证"。我联想到银行实际工作中模型上线前的验证评审环节——道理相通：必须先建立一套自己信得过的离线评价方法，才能判断每次改动是真进步还是碰运气。我决定后续一切改进以本地交叉验证为准。

**（三）调研要"挖到证据"而不是"记住结论"。** 前排方案的文字复盘与其代码实际做法常有出入，只有核对到代码的经验才可靠。这个习惯让我在一周内就形成了一份可直接指导后续工作的借鉴清单，而不是一堆似是而非的印象。

**（四）会用工具，但判断自己做。** 本周借助智能辅助工具（Claude Code）承担了开源代码通读、文档整理等大量事务性工作，效率提升明显；但哪些方向值得做、结论是否可信，必须自己核实和拍板。我理解这也是数据分析岗位在智能化工具普及后的核心价值所在。

## 四、下一周工作计划

围绕答辩考评的"建模流程与实施方案"环节，下周计划：一是基于本周发现撰写**总体技术方案**——数据清洗规则、特征体系设计、"异常识别+分层回归"的模型架构，以及以分层交叉验证为核心的评价方案，并向老师汇报评审；二是把方案落成可执行的**排期与实验管理办法**（先离线验证、后线上提交的纪律）；三是为第三周的编码实现和首轮正式提交做好准备。
